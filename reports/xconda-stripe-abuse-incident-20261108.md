**가장 중요한 판단 3가지**

1. **크레딧 회수 ≠ 손실 회복.** 이미 Seedance 영상 생성에 소진된 크레딧은 외부 API 원가로 **현금이 실제 지출**된 상태입니다. 회수는 계정 잔액을 0으로 만드는 조치일 뿐이며, 피해액은 ① 소비자가 기준(기회원가)과 ② API 실원가(현금 유출)를 **반드시 분리**해 보고해야 합니다.
2. **웰컴 크레딧 500만으로는 1,808,429크레딧을 만들 수 없습니다.** 134계정 × 500 = 67,000크레딧에 불과합니다. 즉 **사용된 크레딧의 대부분은 결제 적립 경로(가결제)로 유입**된 것으로 보이며, 이는 "결제 1건당 적립" 로직이 **반복·중복 호출로 증폭**되었는지 확인해야 한다는 뜻입니다.
3. **계정 삭제는 지금 방향이 반대입니다.** 대표 지시는 "수사 증거 보존을 위해 악용 계정 삭제 보류"인데, 11/08 08:02~08:36에 일반 가입 4,284건이 삭제되었습니다. 악용 의심 134건이 이 삭제 범위에 포함되었는지 **즉시 확인**하고, 앞으로는 **삭제 대신 잠금(lock)** 으로 전환해야 합니다.

## 4. 계정 삭제 관련 리스크 (즉시 확인 필요)

대표 1차 지시 4항은 **"수사 증거 보존을 위해 악용 계정 삭제 보류 및 관련 로그·IP·결제 기록 보존"** 입니다. 그러나 11/08 08:02·08:36 보고에 따르면 일반 가입 계정 **4,284건이 삭제**되었습니다.

| 확인 항목 | 왜 중요한가 | 방법 |
|---|---|---|
| 삭제된 4,284건에 **악용 의심 134건이 포함**되었는가 | 포함 시 계정 귀속 증거 소실 | 삭제 로그(UID·삭제 시각·사유) 대조 |
| 삭제가 **soft delete(플래그)** 인가 **hard delete** 인가 | hard delete면 복구 불가 | DB 삭제 쿼리·백엔드 로직 확인 |
| 삭제 전 **크레딧 원장·결제·IP·생성 이력**이 보존되었는가 | 경찰 제출 자료의 근거 | 백업 스냅샷 존재 여부 |
| "잔여는 소셜 로그인 가입" 의 **잔여 건수** | 소셜 경로로도 악용이 가능한지 판단 | 가입 경로별 집계 |

**권고 조치**

1. **즉시**: 삭제 전 DB 스냅샷/PITR(시점 복구) 가용성 확인 → 없으면 있는 즉시 **별도 스토리지에 export 후 해시 기록**(`sha256sum`) 및 수집 일시 기재.
2. **전환**: 신규 의심 계정은 **삭제하지 않고 `status=LOCKED` + 로그인·결제·생성 차단**. 삭제는 수사 종결 후.
3. **보존 기간 명시**: 로그·IP·결제·생성 이력의 보존 기간(예: 최소 1년)과 접근 권한(지정 인원 2인) 문서화.
4. **원본 불변**: 증거 파일은 읽기 전용 보관, 사본으로 분석. 분석 결과도 "개인/업체를 범인으로 단정하지 않는" 표현 유지(대표 지시 5항).

**최소 요구사항(코드 검증 통과 기준)** — 근거 없는 추측을 피하기 위해, 수정 시 아래 6개를 **명시적으로** 통과해야 합니다.

1. 적립 API는 **서버에서만** 호출되고, 클라이언트가 크레딧 양·상품을 지정할 수 없다.
2. 웹훅은 **서명 검증 + `livemode` 일치** 확인 후에만 처리한다(운영 환경에서 `livemode=false` 이벤트는 수신 즉시 거부·경보).
3. 이벤트 ID · `payment_intent` ID에 **유니크 제약**을 걸어 재전송·중복 호출로 2회 적립되지 않는다.
4. 적립 금액은 **Stripe 객체의 금액·통화·가격 ID**로 서버가 재계산하며, DB 상품 마스터와 불일치 시 적립하지 않는다.
5. 운영 배포 파이프라인에서 `*_test_` 키 사용 시 **빌드 실패**(시크릿 스캔 + 환경변수 검사).
6. 크레딧 원장은 **append-only** + 잔액 재계산(reconciliation) 잡으로 불일치 알림.

## 10. 부록

### 10.1 확인 쿼리 템플릿 (스키마 미확인 — 실제 컬럼명으로 치환)

```sql
-- ① 의심 계정별 사용 크레딧 합계와 상위 소수 쏠림 확인
SELECT uid, SUM(amount) AS used, COUNT(*) AS events
FROM credit_ledger
WHERE amount < 0 AND created_at >= '2026-11-06'
GROUP BY uid
ORDER BY used DESC;

-- ② 결제 이벤트 유니크성 점검 (같은 결제로 2회 이상 적립되었는가)
SELECT payment_intent_id, COUNT(*) AS grants
FROM credit_ledger
WHERE reason = 'purchase'
GROUP BY payment_intent_id
HAVING COUNT(*) > 1;

-- ③ 테스트 모드 결제로 적립된 이벤트 추출 (livemode 미기록이면 이것부터 문제)
SELECT * FROM payments
WHERE livemode = false AND status IN ('succeeded','paid');
```

> ③에서 행이 나오면 **테스트 결제가 운영 적립 로직을 통과했다는 직접 증거**입니다. 이 경우 "왜 통과했는지"를 코드 라인 단위로 인용해야 원인 규명이 끝납니다.

### 10.2 배포·열람 범위 (중요)

`hub.xconda.ai` 는 **GitHub Pages(저장소 루트 서빙)** 이고, `reports/` 아래 파일은 별도 설정이 없으면 그대로 공개됩니다. 본 문서에는 **수사·피해액·대응 상태**가 담겨 있으므로 공개 열람을 전제로 두면 안 됩니다.

**적용한 조치(2026-11-08)**

- `robots.txt` 에 `Disallow: /reports/` 를 추가했습니다. 생성기(`src/content/seo.js` 의 `robotsTxt`)와 CI 가 다시 만드는 `robots.txt` 양쪽에 반영되어, **다음 배포에서도 되돌아가지 않습니다.**
- 회귀 테스트(`scripts/seo.test.mjs`)에 `Disallow: /reports/` 검사를 넣어, 이 줄이 실수로 빠지면 CI 가 실패합니다.

> ⚠️ **robots.txt 는 접근 제어가 아닙니다.** 크롤러의 색인만 막을 뿐, 주소를 아는 사람은 `.md`·`.docx` 를 그대로 내려받을 수 있습니다. 또한 이미 색인된 URL 이 있다면 삭제 요청이 별도로 필요합니다.

**남은 결정** — 공개 저장소에 두는 것 자체가 부담이면 다음 중 하나를 택해야 합니다.

1. 사고 문서는 **비공개 저장소 또는 접근 제한 드라이브**로 이관하고, 공개 저장소에는 요약본만 둔다. *(권장 — 실제 접근 제어)*
2. 저장소는 유지하되 `reports/` 를 `.gitignore` 로 빼고 사내 스토리지에서만 관리한다.
3. 현 상태(robots 차단) 유지 — 색인 방지 수준. **주소 공유 금지**를 전제로 한다.

Google Search Console · 네이버 서치어드바이저에서 `hub.xconda.ai/reports/` 색인 제거를 요청하고, 외부에 `.md`·`.docx` 직접 링크를 만들지 않는 것을 원칙으로 합니다.
